# v0.5.1 Implementation Plan: Source Processing Hardening

> Execution note (2026-05-16): This original planning draft was used as input for
> the repo-accurate task breakdown in `docs/plans/v05.1/`. Follow
> `docs/plans/v05.1/README.md` and the per-task files for implementation. Those
> task files correct this draft's stale `pytest` and `--source-file` examples to
> the repository standard `python -m unittest ...` commands and the current
> `tools/process_source.py --source-type ... --local-path/--url` contract.

## 1. Purpose

This implementation plan defines the concrete task breakdown for v0.5.1.

v0.5.1 is a hardening release for the local source processing pipeline. Its main goal is to make the following flow reliable, testable, and agent-executable:

```text
local source input
  -> ingest
  -> wiki/source summary generation
  -> local rebuild
  -> graph status update
  -> Notion status payload/update
```

This plan exists because the v0.5 source processing flow exposed several integration problems:

- Some modules looked like standalone CLIs but were actually designed as importable helpers.
- `ingest_local.py` expected an ingest-ready body/dict path rather than a simple source file workflow.
- `local_rebuild.py` and `status_notification.py` were not reliably triggered as part of a single source-processing command.
- Notion status did not automatically reflect successful ingest and graph rebuild.
- The failure around Lodestone 7.5 patch note ingestion was not locked down by regression tests.

The outcome of v0.5.1 should be a stable, documented, regression-tested source processing entrypoint.

---

## 2. Non-goals

v0.5.1 must not expand scope into later automation layers.

The following are explicitly out of scope:

- Discord bot command implementation
- scheduler loop
- Notion polling loop
- automatic crawler
- vector database integration
- embedding model integration
- Google Drive as the primary source store
- full RAG answer generation
- multi-bot architecture
- PDF/OCR ingestion unless already supported by existing code

v0.5.1 is only about making local source processing reliable.

---

## 3. Target User Workflow

After v0.5.1, the intended user-facing workflow should be:

```bash
python tools/process_source.py --source-file /mnt/d/ffxiv-bot-storage/raw/lodestone-7-5.html
```

or, if URL fetching already exists and is in scope:

```bash
python tools/process_source.py --url <lodestone_patch_note_url>
```

Expected behavior:

1. The source is read or fetched.
2. The source is stored under local storage.
3. A row is created or updated in the local database.
4. Wiki/source summary generation is triggered if applicable.
5. Local rebuild is triggered.
6. Graph status is updated.
7. Notion status payload is built and pushed if Notion integration is configured.
8. The command exits with a clear success or failure report.

The user should not need to manually import or call `ingest_local.py`, `local_rebuild.py`, or `status_notification.py` for normal source processing.

## 4. Canonical Module Contract

### 4.1 Public entrypoint

`tools/process_source.py` is the only official user-facing entrypoint for v0.5.1 source processing.

It may provide CLI options such as:

```text
--source-file PATH
--url URL
--title TITLE
--source-type TYPE
--storage-root PATH
--db-path PATH
--dry-run
--skip-notion
--skip-rebuild
```

The exact option set should follow existing project conventions. Do not add unnecessary options if the current codebase already has a simpler contract.

### 4.2 Internal helpers

The following modules should remain importable helpers unless there is already a documented reason to expose them as CLIs:

```text
tools/ingest_local.py
tools/local_rebuild.py
tools/status_notification.py
tools/fetch_url.py
```

These modules may have small `if __name__ == "__main__"` guards for debugging only if useful, but v0.5.1 should not require users or agents to call them directly.

### 4.3 Required rule

Normal source processing must go through:

```text
tools/process_source.py
```

Not through:

```text
tools/ingest_local.py
tools/local_rebuild.py
tools/status_notification.py
```

## Task 3. Normalize `process_source.py` as the Official Entrypoint

### Goal

Implement or normalize `tools/process_source.py` so it becomes the single command that performs local source processing.

### Files likely to edit

```text
tools/process_source.py
tools/ingest_local.py
```

### Required behavior

`process_source.py` must support processing a local source file.

The minimum supported command should be:

```bash
python tools/process_source.py --source-file <path>
```

If the repository already uses a different but equivalent argument name, keep the existing style and document it.

### Implementation requirements

The entrypoint should:

1. Parse CLI arguments.
2. Read the local source file.
3. Derive a title if none is provided.
4. Pass a normalized input object into the ingest helper.
5. Receive a structured ingest result.
6. Pass the resulting `source_id` to rebuild.
7. Pass the final result into status notification.
8. Print a concise final status summary.
9. Exit non-zero on unrecoverable failure.

### Suggested internal flow

```text
main(argv)
  -> parse_args(argv)
  -> load_source_input(args)
  -> ingest_local.ingest_source(...)
  -> local_rebuild.rebuild_source(source_id, ...)
  -> status_notification.build/send update(...)
  -> return exit code
```

Names should match the existing code style. Do not rename working functions unnecessarily.

### Red test required?

No new red test beyond Task 2 unless missing edge cases are discovered.

### Verification

Run:

```bash
pytest tests/test_v051_process_source.py
```

Then run a dry-run/manual command if supported:

```bash
python tools/process_source.py --source-file <fixture-or-sample-path> --dry-run
```

### Done criteria

Task 3 is complete when:

- `process_source.py` is the documented entrypoint
- local file input no longer requires manual import usage
- tests for source-file input pass
- errors are reported with clear messages

## Task 4. Stabilize the Ingest Helper Contract

### Goal

Make `ingest_local.py` safe to call from `process_source.py` without ambiguity.

### Files likely to edit

```text
tools/ingest_local.py
tests/test_v051_process_source.py
```

### Required behavior

`ingest_local.py` should expose an importable function that accepts normalized source data and returns a structured result.

The function should return enough information for downstream steps:

```text
source_id
title
source_type
status
raw_path
summary_path, if generated
graph_status, if known
error, if failed
```

The exact return type can be a dict, dataclass, or existing project-specific type. Prefer the current project style.

### Implementation requirements

Do not make `ingest_local.py` responsible for the entire pipeline.

It should handle only ingestion-related work:

```text
input normalization already done or passed in
raw storage
DB row insert/update
basic metadata extraction
optional summary trigger only if already part of existing ingest contract
```

It should not independently call Notion unless that is already the existing design and cannot be safely separated.

### Red test required?

Only if a new bug is discovered while implementing Task 3.

### Verification

Run:

```bash
pytest tests/test_v051_process_source.py
```

Also run any existing ingest-specific tests:

```bash
pytest tests -k ingest
```

### Done criteria

Task 4 is complete when:

- `process_source.py` can call ingest through a stable function
- ingest returns a structured result
- source file input does not require external manual body construction
- existing ingest tests still pass

## Task 5. Integrate Local Rebuild as a Library Call

### Goal

Ensure rebuild happens automatically after successful ingest through `process_source.py`.

### Files likely to edit

```text
tools/process_source.py
tools/local_rebuild.py
tests/test_v051_process_source.py
```

### Required behavior

After ingest succeeds, `process_source.py` should call local rebuild with the correct `source_id`.

Expected flow:

```text
ingest result status = ok
  -> call rebuild(source_id)
  -> receive graph_status
  -> merge graph_status into final pipeline result
```

### Rebuild result contract

The rebuild step should return a structured result such as:

```text
source_id
graph_status
rebuilt_files
error
```

Use the existing return style if already defined.

### Failure handling

If ingest succeeds but rebuild fails:

```text
source status should not be reported as fully graph-built
pipeline result should clearly say rebuild failed
Notion payload should reflect the partial failure if status notification runs
command should exit non-zero unless the existing project convention treats rebuild failure as soft failure
```

### Red test required?

Already covered by Task 2.2. Add a new red test only if rebuild failure behavior is undefined.

### Verification

Run:

```bash
pytest tests/test_v051_process_source.py
pytest tests -k rebuild
```

### Done criteria

Task 5 is complete when:

- process_source triggers rebuild automatically after ingest
- rebuild receives the correct source_id
- graph status is included in the final result
- rebuild failure is visible and test-covered

## Task 6. Integrate Status Notification After Rebuild

### Goal

Ensure Notion status is updated or at least buildable from the final pipeline result.

### Files likely to edit

```text

tests/test_v04_status_notification.py
tests/test_v051_process_source.py
```

### Required behavior

`status_notification.py` should be called after ingest and rebuild have produced a final result.

The status update should distinguish:

```text
ingest failed
indexed but graph pending
indexed and graph built
rebuild failed
notification skipped
notification failed
```

### Payload rules

The Notion payload must be small and status-oriented.

It should include only fields like:

```text
title
source_id
source_type
status
graph_status
summary_path
raw_path, if useful
error message, if useful
updated_at
```

It must not include raw-heavy fields like:

```text
body
raw_body
raw_html
attachments
drive_url
```

### CLI flags

If useful, support:

```text
--skip-notion
--dry-run
```

`--dry-run` should build and print or return the status payload without sending a real Notion update.

### Red test required?

Yes if the payload exclusion test does not already exist.

### Verification

Run:


### Done criteria

Task 6 is complete when:

- status notification is integrated into the official pipeline

## 7. Red Test Policy

A red test is required whenever the task fixes a behavior that previously failed or was ambiguous.

Red tests are required for:

```text
source-file input regression
process_source triggering rebuild
status promotion from graph_status=built
pending graph status not being falsely promoted
Notion payload excluding raw-heavy fields
Lodestone-like HTML ingestion
end-to-end local source processing
```

Red tests are not required for:

```text
discovery-only inspection
documentation-only changes
small refactors that do not change behavior
renaming internal variables
```

When adding a red test, the agent must report:

```text
- test name
- expected failure before implementation
- implementation change that makes it pass
- final passing command
```

## 8. Safety Rules for Implementation

Follow these rules during implementation:

1. Do not silently change storage root conventions.
2. Do not reintroduce Google Drive as the primary source store.
3. Do not require real Notion credentials for tests.
4. Do not make network calls in automated tests.
5. Do not store large raw HTML bodies in Notion payloads.
6. Do not convert every helper into a public CLI unless the spec explicitly requires it.
7. Do not bypass the local DB if the current architecture expects DB-backed source tracking.
8. Do not collapse ingest, rebuild, and notification into one untestable function.
9. Do not remove existing v0.4/v0.5 behavior without a regression test proving the new behavior.
10. Do not update unrelated files outside the v0.5.1 scope.

## 9. Expected Final Architecture

The target architecture should look like this:

```text
User / Agent
    |
    v
python tools/process_source.py --source-file <path>
    |
    +--> load source file
    |
    +--> tools.ingest_local
    |       |
    |       +--> local storage
    |       +--> local DB source row
    |
    +--> tools.local_rebuild
    |       |
    |       +--> wiki/source summary or graph artifacts
    |       +--> graph_status
    |
    +--> tools.status_notification
            |
            +--> build compact Notion payload
            +--> send or dry-run status update
```

The important architectural rule is:

```text
process_source.py orchestrates the pipeline.
ingest_local.py ingests.
local_rebuild.py rebuilds.
status_notification.py builds/sends status.
```
